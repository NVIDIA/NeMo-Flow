Use the `nemo-relay-openclaw` plugin to apply NeMo Relay middleware and
observability to OpenClaw model calls in process. OpenClaw's original stream
function continues to own authentication and network transport. The plugin
wraps that function with NeMo Relay and does not use the NeMo Relay Gateway, a
plugin endpoint, or destination headers.

Managed model calls support LLM guardrails, request intercepts, execution
intercepts, stream execution intercepts, adaptive behavior, and observability.
OpenClaw's public tool hooks also support tool guardrails, tool request
intercepts, and live tool spans. Tool execution intercepts are unsupported
because those hooks do not expose the tool execution callback.

## Requirements

The integration requires the following software:

- OpenClaw `2026.9.3` or newer and earlier than `2027`.
- The OpenClaw CLI available as `openclaw`.
- A host supported by the `nemo-relay-node` package.

## Install the Plugin

Install the plugin through OpenClaw and restart the gateway:

```bash
openclaw plugins install npm:nemo-relay-openclaw@0.8.0
openclaw gateway restart
```

Use `nemo-relay-openclaw` as the package name. Use `nemo-relay` as the plugin
ID in OpenClaw configuration, inspection, and gateway status commands. The
OpenClaw peer dependency is optional, so installing this package does not
install a second OpenClaw copy.

For a project-local installation instead, run:

```bash
npm install nemo-relay-openclaw@0.9.0
```

Use `openclaw plugins install` when OpenClaw should register and manage the
plugin.

## Configure the Provider

Add `nemo-relay` to `plugins.allow` and configure the plugin under
`plugins.entries["nemo-relay"].config`:

```json
{
  "plugins": {
    "allow": ["nemo-relay"],
    "entries": {
      "nemo-relay": {
        "enabled": true,
        "hooks": {
          "allowConversationAccess": true
        },
        "config": {
          "enabled": true,
          "plugins": {
            "version": 1,
            "components": []
          },
          "routing": {
            "favorites": ["openai/gpt-5.4", "anthropic/claude-sonnet-4-5"]
          },
          "fallback": {
            "enabled": true
          }
        }
      }
    }
  }
}
```

The configuration fields have the following behavior:

- `enabled` enables the provider and lifecycle integration.
- `plugins` contains the standard NeMo Relay plugin-host configuration for
  guardrails, intercepts, adaptive behavior, subscribers, and exporters.
- `routing.favorites` publishes selected upstream routes in the OpenClaw model
  catalog. Compatible routes can still be entered manually.
- `fallback.enabled` enables live, observability-only LLM handles for
  unprefixed provider calls. It does not apply LLM middleware to those calls.
- `hooks.allowConversationAccess` lets the plugin receive the conversation
  payloads required by fallback capture.

The integration passes live prompts, responses, tool arguments, and tool
results into Relay. Configure Relay event sanitizers and observability
components to filter or omit sensitive content. The OpenClaw plugin does not
apply a separate capture policy.

The legacy `backend` and `correlation` fields are accepted as deprecated no-ops
for one release. The plugin logs a warning when either field is present.

Refer to [Plugin Configuration
Files](/configure-plugins/plugin-configuration-files) for generic component
configuration and [Observability
Configuration](/configure-plugins/observability/configuration) for exporter
configuration.

Restart the gateway after changing plugin configuration:

```bash
openclaw gateway restart
```

## Select a Managed Model

Use the following model syntax:

```text
nemo-relay/<upstream-provider>/<upstream-model-id>
```

The model ID can contain slashes. For example,
`nemo-relay/openrouter/vendor/model` selects provider `openrouter` and model ID
`vendor/model`. Recursive routes such as `nemo-relay/nemo-relay/...` fail
before execution.

The initial verified routes are listed in the following table:

| Upstream Provider | Supported OpenClaw API                   |
| ----------------- | ---------------------------------------- |
| `openai`          | `openai-responses`, `openai-completions` |
| `openai-codex`    | `openai-chatgpt-responses`               |
| `anthropic`       | `anthropic-messages`                     |
| `google`          | `google-generative-ai`                   |
| `google-vertex`   | `google-vertex`                          |
| `openrouter`      | `openai-completions`                     |

The provider takes a verified route snapshot for each invocation. A Relay
request interceptor can select another model only when that route exists in
the same snapshot and uses a supported provider and API combination. Unknown,
recursive, custom-transport, and unsupported routes fail closed.

OpenClaw's public provider-family compatibility hooks preserve replay
sanitization, tool-schema normalization, reasoning payloads, and supported
stream parameters. At execution time, OpenClaw resolves runtime authentication,
base URL, and request transport overrides for the selected upstream model.

## Understand Live Lineage

The plugin opens every Relay scope before the corresponding work starts:

```text
OpenClaw session
└── agent run
    ├── Relay LLM call
    │   └── upstream provider execution
    ├── tool call
    └── subagent session
        └── subagent run
```

The coordinator stores live identifiers and Relay handles only. It does not
store transcripts or reconstruct calls from message history, `agent_end`, or
late timing events. Completed handles are removed immediately. Incomplete
records have a five-minute time-to-live and a limit of 1,024 records per
category. Gateway shutdown drains remaining handles from leaves to roots and
marks them abandoned.

OpenClaw does not pass `runId` directly to `wrapStreamFn`. The provider first
uses an exact `requestId` and active-run match. Otherwise, it requires exactly
one active run in the session. Managed execution fails closed when the parent
is missing or ambiguous. The supported host invariant is one active agent run
per OpenClaw session.

Run-mode subagent sessions are children of the requester run. Long-lived
subagent sessions are children of the requester session and include causal
metadata for the requester run. A managed child waits up to one second for its
authoritative spawn edge and fails closed instead of opening an orphan scope.
Assistant tool-call IDs link sibling tool spans to the managed LLM call that
produced them.

All asynchronous work uses explicit scope stacks. Concurrent sessions,
subagents, streams, and tools do not mutate a process-global current stack.

## Understand Fallback Capture

Unprefixed model calls can emit observability through the fallback hooks when
`fallback.enabled` is `true`. `llm_input` opens a live LLM handle under the
known run, and `llm_output` closes it. The plugin skips unmatched output and
closes abandoned fallback handles at agent or gateway shutdown.

Fallback capture is fail open and does not reconstruct calls from transcripts,
message writes, model timing hooks, or grace timers. Fallback hooks ignore the
`nemo-relay` provider to prevent duplicate LLM spans.

## Understand Tool Policy

Before a tool executes, the plugin resolves the exact parent run, applies Relay
conditional guardrails and request intercepts, and opens a tool handle with the
rewritten parameters. OpenClaw executes the tool with those rewritten
parameters. The matching `after_tool_call` hook closes the handle with the
actual result, error, and duration.

Tool policy fails closed when the parent run is missing. Relay tool execution
intercepts do not run because the public OpenClaw hook does not provide the
execution callback. This is the only unsupported Relay interception type.

## Verify the Integration

Inspect the installed plugin:

```bash
openclaw plugins inspect nemo-relay --runtime --json
```

Run a managed model such as `nemo-relay/openai/gpt-5.4`, then inspect the
admin-scoped runtime status:

```bash
openclaw gateway call nemoRelay.status --json
```

The response reports whether the runtime is in process, whether the plugin host
initialized, active handle counts, and counters for missing runs, ambiguous
runs, orphan subagents, and ambiguous spawn tools. It also reports
`toolExecutionIntercepts: false` and `gateway: false` as explicit capability
boundaries.

Verify the configured subscribers or exporters after the session ends. For
example, confirm that ATIF output files exist or that typed OpenTelemetry spans
arrived at the configured collector.

## Troubleshooting

If a managed model fails before execution, check the following conditions:

- The model uses `nemo-relay/<provider>/<model>` syntax.
- The upstream model exists in OpenClaw's current model registry.
- The provider and API combination appears in the verified route table.
- The session has exactly one active run, or `requestId` exactly matches its
  active `runId`.
- A managed subagent has an unambiguous requester and spawning-tool edge.

If fallback output is absent, verify `fallback.enabled`,
`hooks.allowConversationAccess`, and the availability of matching `llm_input`
and `llm_output` hooks. Use `nemoRelay.status` counters to distinguish skipped
fallback records from strict managed-lineage failures.

If no exported output appears, verify the generic NeMo Relay plugin component
configuration and the destination's availability. The OpenClaw integration
runs entirely in process; starting a separate Relay Gateway does not affect its
provider traffic.
